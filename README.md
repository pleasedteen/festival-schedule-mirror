# 戏剧节服务台

从各剧场的 HTML 公告中采集现行排期，回答“到哪个剧场、几点入场”。
项目使用 **TypeScript + Node.js + DuckDB**，自带可在本地运行的模拟公告站。

## 快速开始

```bash
npm install          # 安装依赖（含 DuckDB 预编译二进制）
npm run build        # 编译到 dist/

# 终端 1：启动模拟公告站（默认 http://127.0.0.1:8787）
npm run mock

# 终端 2：采集并查询
npm run collect -- --site http://127.0.0.1:8787
npm run query -- event E-1005
npm run query -- venue studio
npm run query -- all
npm run query -- pending
```

默认数据库为 `data/festival.duckdb`，可用 `--db <路径>` 指定。

### 一条命令验证

```bash
npm test
```

安装依赖后运行，**80 秒内**（实测约 2–5 秒）自动完成以下验证并输出可读结果：

1. **翻页恢复**：采集第 2 页时会话被轮换，翻页签名失效返回 409，采集器重新取得入口页并补齐两页公告；
2. **临时限流**：站点返回 429 + `Retry-After` 时按站点给出的时间等待后继续；
3. **公告补采**：缺少入场时间 / 档期为“待定”的公告进入待补采，公告修正后重新采入；
4. **改场前后**：只有一端公告时继续展示最近一次已确认排期并标记待确认；两端到齐后才切换剧场与时间；
5. **重启与续采**：关闭并重新打开数据库后已确认排期仍可查询；采集中断后查询不受影响，随后续采成功；
6. **一致性**：按演出编号与按剧场查询使用同一份已确认结果；
7. 解析与折叠的边界检查（非法日期、占位文字、两端时间不一致、低修订号不覆盖等）；
8. **长列表跨进程续采**：64 页（128 条）模拟列表，每剧场每进程最多 30 次列表请求，分三个进程采齐；
   覆盖会话轮换后的入口深翻恢复、未完成/完成状态区分、未完成期间已采排期可查、稳定后单请求复查、
   中途重排从头重走、增删后按当前完整列表收敛。

另有快速单元检查：`npm run test:unit`。

### 长列表与跨进程续采

- 每个**剧场**在**单个进程**内最多发出 **30 次列表请求**（含 429 重试与 409 恢复请求），这是硬上限；
- 到达上限不算失败：命令标记**未完成**并退出码 `3`，续采游标（下一页页码、已覆盖页码、已见公告键、列表指纹）
  持久化在 `collect_cursors` 表；下次运行（包括全新进程）凭入口 `/venue/<id>?page=N` 直接深翻到下一页继续；
- 会话轮换使旧翻页链接返回 409 时，同样从入口带 `?page=N` 重新取得当前页的新签名后继续，不必从第 1 页重走；
- 列表指纹随公告**增删、重排、修订**变化；指纹一变，旧游标作废并从第 1 页重走一轮；
- 只有完整覆盖 `1..总页数` 的一轮才标记**完成**（退出码 `0`），并把该剧场公告收敛成本轮实际见到的完整列表，
  撤下/重排产生的陈旧公告在此一次性移除；未完成期间不删除任何数据，已采排期始终可查；
- 已采齐且指纹未变时，再次采集只请求入口第 1 页核对，单次请求即确认整份列表仍有效。

采集命令退出码：`0` 全部采齐；`3` 有剧场未完成（可续采，已采排期可查）；`1` 有剧场失败；`2` 参数错误。

## 业务规则

| 场景 | 行为 |
| --- | --- |
| 公告解析可靠 | 写入 `announcements`，参与排期折叠 |
| 无法可靠解析（缺时间、缺编号、时间非法等） | 标记为**待补采**，不影响其他公告；修正后重新采集即可进入排期 |
| 同一演出跨剧场 | 沿用同一 `eventId`，按该演出的 `revision` 排序 |
| 改场 | 原剧场端与新剧场端分别发布；仅收到一端时继续展示最近一次已确认排期并标记“改场待确认” |
| 两端确认 | 方向一致且演出/入场时间一致，才对外切换剧场与时间 |
| 取消公告 | 独立生效，不需要另一端 |
| 查询一致性 | 采集结束后统一把结果折叠到 `effective_events` / `change_confirmations`；按编号与按剧场查询都只读这两张表 |
| 采集中断/重启 | 公告按 `ann_key` 幂等入库；启动时依据公告重建派生排期，已确认结果仍可查询，续采接上此前未确认的改场 |
| 长列表请求上限 | 每剧场每进程最多 30 次列表请求；到达上限标记“未完成”（退出码 3），游标落库，跨进程从下一页续采 |
| 会话轮换 | 旧翻页签名 409 后从入口 `?page=N` 深翻恢复当前页，不重走已采页面 |
| 列表增删/重排 | 列表指纹变化即作废旧游标并从第 1 页重走；完整覆盖后才标记完成并按当前完整列表收敛旧公告 |

## 数据模型

- `announcements`：每条公告一行（`ann_key` 为幂等键），保留原始 HTML、来源页、版式与解析状态；
- `effective_events`：每个演出一行，服务台唯一对外使用的“已确认排期”（剧场、演出时间、入场时间、待确认/待补采标记）；
- `change_confirmations`：每个（演出, 修订号）的改场两端确认状态与理由；
- `venue_sync`：每个剧场最近一次采集的页数、请求次数、翻页恢复次数、限流等待次数、状态（`complete` / `incomplete` / `failed`）与错误；
- `collect_cursors`：每个剧场的跨进程续采游标——列表指纹、下一页页码、总页数、本轮已覆盖页码、本轮已见公告键、是否已采齐。

```
  parse/parse.ts         新版/旧版 HTML 解析（cheerio）
  parse/venues.ts        改场文本中的剧场识别
  collect/collector.ts   翻页、会话恢复、限流等待、幂等入库
  db/store.ts            DuckDB 存储与派生排期刷新
  query/desk.ts          查询服务（按编号 / 按剧场 / 待补采）
  query/view.ts          输出格式化
  mock/content.ts        模拟公告内容（三个剧场、两种版式、三个内容版本）

```

## 模拟公告站

- 入口：`/venue/grand`、`/venue/studio`、`/venue/harbor`；
- 每页 2 条公告，共 2–4 页；`grand`/`harbor` 为新版式，`studio` 为旧版式；
- 翻页链接形如 `/venue/grand/page/2?sig=...`，签名绑定会话 cookie 与翻页令牌；会话轮换后旧链接返回 `409`；
- 内容版本（演示/测试用）：

```bash
curl -X POST http://127.0.0.1:8787/_control/content \
     -H 'content-type: application/json' -d '{"version":2}'
```

  | 版本 | 变化 |
  | --- | --- |
  | 1 | 初始公告（含待补采） |
  | 2 | 海港剧场修正《暴风雨》入场时间；实验剧场补全《等待戈多》档期 |
  | 3 | 海港剧场补发 E-1005 改场公告，与实验剧场一端配对确认 |

- 其他控制：`/_control/session/rotate`、`/_control/rotate-after`、`/_control/rate-limit`、`/_control/abort-after`、`/_control/stats`、`/_control/reset`。
- 长列表与列表变动（测试用）：

```bash
# 把某剧场替换为 128 条（64 页）长列表
curl -X POST http://127.0.0.1:8787/_control/long-list \
     -H 'content-type: application/json' -d '{"venue":"grand","items":128}'
# 中途重排（交换两个 0 基下标）、撤下（removeAt）或补发（prepend）
curl -X POST http://127.0.0.1:8787/_control/list-edit \
     -H 'content-type: application/json' -d '{"venue":"grand","swap":[0,5]}'
```

  入口页支持深翻续采：`/venue/grand?page=31` 凭当前会话直接返回第 31 页及新的翻页签名；
  每页 HTML 的 `<body>` 带 `data-page` / `data-page-count` / `data-list-token`，供采集器识别位置与列表指纹。
